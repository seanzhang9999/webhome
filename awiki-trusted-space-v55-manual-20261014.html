阅读说明与版本依据

本说明书面向产品、架构、研发、演示主持人与合作方，完整解释 AWiki V5.5 的产品结构、协同对象、权限分工、PET 科研演示与工程边界。AWiki 在本方案中以方案包提供共同业务语义，以空间建立协同边界，以事项组织人机协作，以 Board 和 Artifact 保留可追溯的工作内容与确认结果。

V5.5 当前交付形态是一个自包含 HTML 前端演示。它可以运行本地状态机、切换四个人员视角、执行模拟准入和分别确认，但没有接入真实账号、远程模型、材料数据平台、A2A 网络或实验设备。本文的“已实现”专指该前端中的可运行能力；“模拟”说明数据与身份的证据性质；“待实现”指生产系统能力。

1 AWiki 五个一级入口

AWiki 的一级入口为“消息、一览、连接、AWiki、工作”。设置位于导航底部，是辅助入口，不计入这五个业务入口。L0–L7 是材料科研方案的业务模块，不是 AWiki 全局导航。V5.5 首次加载默认进入“工作 → 事项”，角色为材数智元张研，空间为 PET-SPACE-001，进度为 1/19。[S01、S02]

入口产品职责本演示的性质
消息人与 Agent 的沟通、通知及会话入口预置消息/会话展示；未连接外部 IM。

2 工作四对象与持久协作关系

“工作”下设事项、资源、空间、方案四个对象入口。四者不是四套重复数据：事项组织一次具体工作，资源登记可引用对象，空间约定协作边界，方案保存可复用能力和契约。专题在空间内部组织长期知识，不再作为工作一级对象。[S01、S03]

对象承载内容与其他对象的关系
事项 Matter目标、参与者、群消息、输入输出及交接关口以人机混合群展示；批准交接后继续推进才出现后续事项。
资源 ResourceBoard、任务 Artifact、来源文件等可索引对象群与专题引用资源；多处引用不意味着拥有多个独立原件。
空间 Space成员资格、治理提案、专题、运行状态与演示管理约束事项及资源的协作范围；空间成员不自动拥有所有资源权限。
方案 Pack角色、Schema、模板、业务模块、Agent/Skill 与治理约定为一个或多个空间提供共同语言；本次仅一个固定材料科研包。

事项按工作边界形成

PET 示例形成四个事项群：需求协同群承接 L0–L3；方案设计群承接 L3–L5；TC-01 实验执行群承接 L6–L7；下一轮协同群承接 L7 回流到 L4。不存在“一层一个聊天室”的固定要求。群的建立取决于交接状态及推进事件，而非专业模块编号。

持续对象与一次输出

Artifact 是任务输出；Board 是持续维护共同事实、责任和讨论的工件。Board 在资源中有独立页面与标识，事项群引用它，确认回单返回来源事项。专题可收录候选知识，方案保留可复用模板；不能把某次模拟实验结果直接升级为通用科研能力。

典型关系为：方案定义任务与工件契约 → 空间确认成员和治理 → 事项提出工作 → Agent/人员形成 Artifact → 必要时在 Board 共同确认 → 最小范围交给下一事项。关系存在不代表授权自动传递。

3 方案包安装与 Pack Space 多对多

方案包是跨主体可复用的协同能力与协议集合，包含业务语义、角色、Board/Artifact/Resource 契约、Agent/Skill、治理模板、界面和可选流程。客户端安装兼容包后，才具备理解同类协作的能力；具体空间是否允许加入，仍由其治理规则决定。[S04]

设计关系与当前实现

架构上 Pack 与 Space 是多对多：同一个 Pack 可供多个空间使用，一个空间也可组合多个兼容 Pack。V5.5 实际只保存 awiki.materials-research@1.0 一个固定包，配有多个独立演示空间。它展示了“一包多空间”，没有实现多包组合、依赖解析、发行签名、升级或真实兼容性校验。Manifest 中的 compatibility 字段是声明，不是运行中的版本解析器。

层次设计中的对象V5.5 实际状态
包定义包标识、版本、契约、角色与能力固定材料科研包 1.0；内容由页面常量和模板表达。
安装不同客户端分别安装兼容能力registry.installs 中三个组织键的布尔状态；没有下载或部署程序。
成员资格某组织获得某空间准入各空间 participants 独立保存 joined、invited 等状态。
个人职责组织内人员分别承担责任张研与周博士各有视角和签收权限，共享 research 组织安装与准入。
多空间使用同一组织在多个空间独立协作初始提供 001 与 002，可创建 003 等全新演示实例。

安装不等于授权

客户与材数智元初始已安装并加入；合作实验室初始未安装、未获邀请。王工必须切换到自己的模拟客户端安装，再按规则加入。周博士不需要作为第四个机构安装或申请入会；orgOfPerson 将 reviewer 映射为 research，但这种继承只解决组织资格，不赋予张研的个人签收权限。

生产实现应将组织许可、客户端安装、个人登录、代理授权、空间角色和资源能力分开建模。V5.5 的组织布尔值不能证明每个人的真实设备已安装程序，也不能证明其专业资格已验证。

4 空间成员资格与三种治理模式

空间是由成员、规则、身份关系和授权组成的逻辑协同边界。空间可以由不同主体共同参与，并由独立运营商托管协调服务；它不要求所有私有数据集中上传到同一数据库。

治理模式规则含义V5.5 支持边界
单方管理由明确治理主体决定准入及规则变更页面解释该模式；没有可运行的模式切换及单方准入场景。
多方共治按约定阈值由多个治理主体共同决定已实现固定 G-017 提案：客户与材数智元各确认一次，实验室才获邀请。
协议自治根据既定凭证、资格、版本和策略自动判断常规请求只有文字及 Manifest 示例；没有凭证验证、策略引擎或自动准入执行。

G 017 的实际流程

客户李工与材数智元张研分别在自己的视角确认邀请。双方齐备后，participants.lab 变为 invited；王工安装方案包后自行加入，状态变为 joined。未切换到对应角色的投票、未安装时加入，都被演示逻辑阻止。王工也可通过准入引导提交加入申请，但申请不代替双方批准。[S05]

周博士不参与这一机构准入投票：虽然与张研属于 research 组织，其当前个人角色 reviewer 不等于 governance 操作要求的 research 键。组织内专业复核权和机构治理代表权不能混用。

授权不会因入会自动扩张

提案批准只建立成员资格。客户配方仍须由客户控制者授权；Board 仍按指定角色确认；实验室设备仍由实验室的执行与安全责任体系控制。Manifest 说明这些原则，但本页没有真实数据 API 或设备入口来执行策略。[S05、S06]

协议自治需要规则发布、有效期、撤销、争议与异常处理。V5.5 没有实现治理规则升级、机构退出、成员撤销、多方签名验签或跨服务商同步，不能把固定两次点击解释为完整治理平台。

5 治理 托管 数据与执行的权责分离

同一机构可以兼任多种角色，但每项权力应有独立来源。决定谁能加入空间、维护协同服务、授权读取数据、确认 Board 以及执行任务，是不同动作。把这些权力合并给“管理员”会破坏跨主体协作的边界。

责任层决定或执行什么不能据此获得什么
空间治理成员准入、规则版本、治理提案所有配方、所有 Board 和实验设备的默认控制权。
基础设施托管目录、消息路由、协同状态、索引、通知、恢复治理代投权、数据所有权、替成员签收的权力。
数据控制数据范围、用途、期限、来源条件和共享对象其他机构资源的授权权；空间资格不能转授他方数据。
Board 控制共同事实、责任、协作成员、版本、交接结论自动启动设备或把建议变成已验证实验事实。
任务执行人员接单、SOP 核对、设备安全边界、执行回单替客户改需求，或替专家完成独立专业复核。
个人专业复核核对证据性质、缺失检测和下一轮研究建议同组织其他个人的项目交接确认权。

建议的生产分层

治理控制面管理 Manifest、提案及成员；协同服务面管理事项、Board、引用与回单；策略决策点判断请求；数据 API、工件下载与设备适配器的策略执行点负责真正阻断；审计服务记录可验证事件。AWiki 可托管这些服务的一部分，但不能因为托管而自动成为数据控制者。

V5.5 仅在同一页面中模拟这些角色。下拉框切换不是登录，隐藏列表不是资源安全隔离，本地 activity 日志不是不可篡改审计。真实身份、服务端鉴权、授权撤销、端点强制执行及审计保全均属于后续实现。

版本和持续讨论

参与者先选本轮结论，再分别确认。全部指定职责完成后自动形成确认快照，记录 frozenVersion，并将回单写回来源事项。选择不同结论会清空本轮 acks、个人审计和待确认提案，避免沿用旧同意。确认后仍可讨论或提出变更建议，但不会自动覆盖冻结结论。

当前数据结构区分 version 与 revision：评论、确认等会推进 revision；确认冻结的是 version。页面没有完整的新业务版本创建、重开审批和差异合并流程，因此不能将“可继续讨论”写成“已实现多版本修订闭环”。

独立链接的实际限制

复制链接使用 #board=spec 等地址片段。链接只定位当前浏览器已有状态中的 Board，不携带空间 ID 或完整对象数据，也没有远端共享数据库。换浏览器、换设备、清空存储或切换空间后，不保证打开同一份工件。业务 ID BRD-PET-… 与右侧提示用的 BOARD-RESULT-HANDOFF 等显示标签属于不同命名表示，不应混作网络全局标识。

8 群聊双向引用与私人 AI 伙伴

群聊首先是自然讨论。用户直接输入并发送时，消息保持原文；通过加号显式关联 Board、Artifact 或 TC-01 任务时，才增加引用。Board 讨论可标记为讨论、待答问题或变更建议。引用不会自动代表批准、接单或发送给新的主体。[S09]

双向引用的实际链路

关联 Board 的群消息记录 boardId；Board 的 activity 记录 sourceMessageId、sourceGroup、sourceSpace。读者从群内引用进入 Board，再从协作记录中的回链定位来源消息。变更建议进入 changeRequests，并保持 needs_review；它不会直接替换共同事实或已冻结结论。历史事项输入被禁用，回看旧群不等于继续在旧群推进。

左右联动与主动提醒

左侧事项/Board 是正式工作面；右侧 AI 伙伴根据当前对象、成员资格和本方签收状态提示“先完成准入”“轮到你确认”“等待其他主体”等，并可定位左侧相应任务、展开核对要点。右侧不形成第二套签收按钮，也不会替人点击确认。[S10]

所谓主动提醒是页面状态驱动的规则提示；草稿建议来自本地关键词与预置逻辑。它不是后台常驻 Agent、实时大模型推理、系统推送或定时监控。私人伙伴不是事项群成员，私人笔记与建议不会因查看而自动发送到群。

已知隔离缺陷：私人笔记只按事项保存和读取，没有按个人角色过滤。本次实测在张研视角保存笔记后，切到同一事项的周博士视角仍可看到。因此“私人”目前是工作面语义，不能理解为已实现个人数据隔离；真实使用前必须修复。

16 空间级演示管理的准确语义

入口为“工作 → 空间 → 演示管理”。V5.5 的状态保存在浏览器 localStorage；各空间运行状态独立，安装状态在 registry 层共享。该机制方便教学和回放，不是生产多租户安全隔离。[S14]

操作实际修改范围应当如何讲解
导出当前空间 JSON不改状态；导出 Manifest、当前 state、安装状态与导出时间用于本地留存；没有与之配套的完整导入恢复界面。
只读历史回放只改变 replayIndex，不改 cursor、确认和回单逐条阅读已发生事件；不是恢复任一历史时刻的完整对象快照。
复制为新演示空间新 Space ID 与 DEFAULT 初始状态，原空间保留实际是创建新初始实例，不复制当前进度、评论、签收或实验回单。
恢复当前空间初始快照重置当前 state，清除本空间草稿关联等临时交互状态清除进度、运行 Board、确认、备注、执行回单、专题收录及模板等运行数据。
重置后仍保留空间 ID、participants、proposal、references、包安装和其他空间成员资格、治理投票和跨空间引用仍在；不是清空该空间全部元数据。

可复现的隔离检查

先运行空间 001 至完成并导出。创建 003 后，确认 003 从 1/19 开始，切回 001 仍为 19/19。重置 001 后确认其回到 1/19，再查看已安装包和实验室成员状态仍保留；其他空间不受影响。需从未邀请实验室的状态重新讲解准入时，应创建新演示空间。

跨空间引用的当前限制

客户视角可将已确认需求 Board 的引用登记到找到的第一个其他空间。只登记源空间、Board ID、版本和范围等元数据，不复制完整快照内容，也没有目的空间选择器、撤销传播或有效性校验。源空间重置后，目标空间引用可能仍保留，不能当成可验证的冻结副本。

重置不修改 GitHub 文件，不卸载方案包，也不能撤销任何真实外部操作。生产空间需要归档、撤销与保留规则，不能照搬本地演示的清空方式。

17 与 A2A OA 流程引擎及可信数据空间的关系

对象或系统承担的职责与 AWiki 的关系及边界
A2A ArtifactAgent Task 的输出，由一个或多个 Part 承载V5.5 展示 artifactId、name、description、parts、metadata 等示例；没有网络互操作。[R04]
AWiki WorkArtifactRecord长期工作关联、来源、依赖、授权范围、Board 回单和证据性质应用层工作记录；不属于 A2A 核心标准字段，也不替代原生 Artifact。
Board共同事实、讨论、版本、责任与交接确认可以引用多个 Artifact；签收是局部动作，不应简化为结果 JSON 或审批按钮。
OA 审批组织既定审批事项和审批轨迹可作为某组织内部授权来源；不能仅凭一次 OA 通过推定其他机构已同意或设备已获授权。
流程引擎调度顺序、依赖、重试、状态和人工关口可作为方案执行组件；Pack 还含角色、语义与工件契约。当前 E 数组只是固定事件序列。
可信数据空间在共同规则下组织数据使用与参与者协作治理、运营、数据控制需区分；AWiki 当前表达这一架构方向，不证明已部署完整可信数据空间。[R05]

A2A 解决 Agent 之间的任务与结果交换，不自动定义本场景的组织治理、专业复核与长期知识复用。源码将 a2aArtifact 与 awikiRecord 分开生成是合适的职责划分，但“形态相似”不能替代相应版本的 Schema 校验和独立端点联调。

同样，Board 共同确认不能自动推导成设备执行许可或法律电子签署。真实接入时，应把组织内部审批结果、空间资格、资源授权、个人职责与任务执行点的校验逐层关联，并保留各自依据。本文不将这些建议写成已经完成的集成。

方案包负责提供业务共同语言，流程引擎负责运行编排，A2A 可承载任务输出交换，可信数据空间规则负责跨主体的数据使用边界，Board 保留具体工作中的共同事实与责任。这些组件可以组合，但没有一个组件能独自替代其他所有职责。

20 源码遗留差异与后续工程重点

V5.5 已补齐内部专家独立视角，但部分早期文案和通用示例仍保留旧措辞。说明书采用当前角色映射和实际操作行为，避免原样放大这些残留。[S15]

发现准确解释后续建议
hold 确认后仍可推进三个交接关口仅检查 status=confirmed，未检查 choice=approve；已复现推进必须同时验证批准结论；暂缓应保留待处理状态和重开路径。

audit 来源摘要仍写检测方当前周博士 org=材数智元，个人职责为内部复核；没有第四家检测机构统一来源摘要、角色介绍与所有提示文案。
概览与 Manifest 较概念化多方共治标签固定；mode 与 compatibility 不等于完整可切换治理/版本引擎以受验证规则和包清单驱动界面。
重置提示容易理解过宽实际只换 state；成员、提案、references 保留明确区分运行重置与全新演示实例。
跨空间快照仅元数据没有复制受校验内容，源重置也不使引用自动失效增加版本摘要、内容摘要、授权与撤销语义。
链接不含空间身份片段只带 Board 键，依赖当前浏览器状态生产地址绑定稳定对象、空间和授权上下文。
确认后的修订有限继续讨论不会形成完整的新版本提案与重签流程实现版本冲突、变更批准、撤销及历史快照读取。
前端过滤与状态可改角色模拟无法提供真实安全边界将授权检查移到真实数据、Board、下载和执行入口。

从演示走向可验收系统

第一步建立真实组织/个人身份与服务端持久化，保留张研和周博士的职责分离；第二步接入一个真实跨机构任务链，验证最小数据授权、A2A 输出、人工实验回单及来源；第三步补齐撤销、并发、故障恢复、可验证审计与跨服务商迁移。每一步以独立客户端和受控端点的实际结果验收。

正式科研试点还需要真实需求基线、合格的人员授权、原始仪器数据、测试方法、样品链路和专业复核。不能从本演示的成功推进，推导材料性能、食品接触合规或生产可用性。
