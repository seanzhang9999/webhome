执行摘要：从方案包到可信协同空间

AWiki 的核心不应被表述为一个中心化的科研工作流系统，而是以“可安装方案包”为共同业务语言、以“协同空间”为可信边界、以“事项群”为执行组织、以“Board/Artifact”为共同工作对象的开放工作网络。

各主体在自己的客户端或 Agent 环境安装兼容方案包，取得参与某类协作的技术能力；经空间治理授权后，才成为某一具体空间的成员。安装同一方案包可以加入多个彼此隔离的空间；一个空间也可以启用多个兼容方案包。加入空间并不自动取得全部数据或设备权限。

AWiki 可以商业化提供“可信数据与可靠协同空间基础设施托管服务”：空间目录与协调、治理事件验证、工件索引与协作同步、消息与回单路由、审计及迁移。基础设施运营商不必成为空间治理者，更不能仅凭托管身份获得各参与方私有数据和设备的控制权。

本方案使用 PET 基聚酯弹性体研发作为主线，将材数智元的 L0–L7 专业能力、CaiMat-L1 模型主张、合作实验室与人机混合群融入 AWiki。配套 V5 HTML 是前端预置模拟，目的是解释产品逻辑和检验交互，尚未部署真实 ANP、A2A、DID 签名、设备控制或可信数据空间。

一、设计来源与事实边界

业务源材料包括《材料研发需求/问题诊断表》《PET基聚酯弹性体项目首轮验证方案 V0.2》《Demo 流程》和《基于多智能体协同的黑灯实验室操作系统》。前两者提供 PET 研发目标、指标、风险、候选路线与首轮样品建议；后两者提供 L0–L7 流程、实验总控、任务协议和设备适配的规划。

源材料中《Demo 流程》将 L0 定义为“文献与数据增强”，而本轮产品讨论还要求需求理解。建议将“需求理解/版本对照”视为 L0 的入口子阶段，再进入 L0 文献与数据增强；不宣称源材料已完成这项调整。

原始需求表要求 50℃×24h / −24℃×24h 恢复室温后不漏液；V0.2 研发建议提出 60℃×24h / −20℃×24h 并进行三轮循环。两者不同，可能分别承担客户验收与增强验证角色，不能自动互换。应由 L0 Agent 自动发现差异，客户与研发方在研发委托 Board 中澄清。

项目方提到“20 亿材料数据底座”，上传文件没有给出数据条目定义、质量、授权接口和实测覆盖率。说明书仅将其作为项目方提供的能力主张；Demo 不实际访问该数据底座。L6 示例数据均标注 SYNTHETIC_DEMO，不得当作真实科研结论。

二、AWiki 信息架构：五个一级入口与四个工作对象

AWiki.ai 一级入口保持“消息、一览、连接、AWiki、工作”，并有独立设置。消息承载普通人与人/人与 Agent 的沟通，不自动产生工作授权；一览汇总变化、待办和工件更新并回链来源；连接提供主体、Agent、群组、服务关系，但连接不等于获权；AWiki 负责发现公开知识、能力、方案包和社区；工作负责持续工作组织与资源管理。

工作域四个一级对象更新为“事项、资源、空间、方案”。原“专题”下沉到空间内部。事项是按具体工作动态创建的人机混合群；资源是可授权、可索引的 Board、Artifact、文件和外部资源的统一入口；空间是多主体协同边界；方案是安装在不同主体客户端的协同能力包。

不应让所有导航都被当前空间完全过滤。事项和资源默认可跨空间汇总，同时显示来源空间及授权范围；空间页提供本空间事项、资源、专题、成员、治理和演示管理；方案页展示已安装方案包、版本、兼容性及可加入空间。私人资源始终与空间资源区分。

三、核心对象、标识与生命周期

Pack 是可安装、可升级、可组合的业务协同协议与能力包，包含业务语义、本体/Schema、主体角色、Board/Artifact/Resource 契约、Agent/Skill、治理模板、UI 和可选流程策略。

Space 是在兼容 Pack 基础上，经参与主体授权形成的逻辑协同边界。空间有 Space ID、主 Pack 及扩展包、成员角色、治理声明、数据使用规则、协同服务和审计记录。它不必集中存储所有数据。

Matter 是空间内或个人工作中的动态人机混合工作群，承载任务执行、交接、消息与回单。Topic 是空间内部的长期知识组织单元，引用多个 Matter 与 Artifact，不自动获得执行权限。

Artifact 是 Agent、人员或设备产生的任务结果，可保留 A2A 原生格式。Resource 是统一可发现/可引用/可授权访问的资源登记抽象；Board 和 Artifact 是资源中的重要类型。Board 是多主体围绕某项工作持续维护事实、讨论、版本、责任、执行与验收的共同工件，不是一次性审批表。

建议采用独立 Pack ID、Space ID、Matter ID、Board ID、Artifact ID、Resource URI。任何对象均记录来源、版本、控制主体和策略引用；对象可以跨空间被授权引用，但不能因为一个空间引用它而自动取得全部权限。

四、方案包：跨主体共同语言，而不是流程引擎

“装了包才能加入一个空间，但是装了包可以加入多个不同空间”应落实为两步：兼容方案包安装是技术资格条件；空间成员资格仍需治理授权。Pack 与 Space 是多对多关系：一个 Pack 服务多个空间，一个 Space 可启用多个兼容 Pack，但必须声明主包、扩展包、版本协商及角色映射。

不同主体可有不同安装形态：完整 AWiki 客户端、专业 Agent/Skill 容器、受限网页参与端或经授权的协议适配器。对于不安装完整客户端的外部临时参与者，是否允许“轻量方案运行时”满足安装前提，应由 Pack 的兼容性与安全策略定义，不能默许绕过准入。

传统流程引擎主要定义执行节点、分支、并行、重试和补偿；方案包额外定义谁能参与、如何理解业务对象、哪些工件可交换、权限边界和验收责任。方案可调用现有 BPMN、工作流、A2A 调度器或动态 Agent Harness，不应重做所有调度能力。

兼容协商至少检查 Pack ID、协议版本范围、业务 Schema、角色能力、必要 Skill、授权机制和数据分类。不同版本之间通过声明式映射/迁移工具解决，不应默默转换可能改变法律或实验意义的字段。

五、Space：可信协同边界，不是共享租户

空间以共同规则、身份关系和授权构成边界，而不是以“数据必须进入某台服务器”构成边界。一个空间的不同参与者可以运行不同厂商的客户端、Agent 和存储服务；空间目录和协同服务只持有必要的治理状态、工件索引、授权引用及审计摘要。

空间准入的必要条件是：兼容 Pack 可验证、主体身份/代理关系可验证、空间治理规则同意其加入、角色及最小权限已明确。加入不意味着可以读取所有 Board、下载全部 Artifact、控制设备或代表他人签署。

一个 Board 通常有一个初始关联空间和独立控制主体；跨空间使用可采用三种方式：实时授权引用、冻结版本快照、派生新 Board。冻结快照适合实验依据和合规复核；派生 Board 适合另一空间需要独立讨论和承担责任。跨空间引用必须保留上游使用约束和来源关系，不能自动转授未获许可的数据。

六、空间治理：单方管理、多方共治与协议自治

空间需要治理机制，但不必有一个可任意读取所有数据的超级管理员。区分发起主体（Creator）、治理主体（Governor）、基础设施运营商（Operator）、工件控制主体（Controller）、实际执行主体（Executor）。一方可以兼任多个角色，但权力来源必须分别记录。

单方管理适合企业供应链或客户主导研发；多方共治适合客户与科研机构共同制定规则；协议自治适合高标准化开放网络。协议自治并非没有治理：常规准入可以由规则引擎完成，争议、规则升级、失效凭证和异常处理仍需要约定的治理主体或仲裁机制。

建议用 Space Governance Manifest 声明治理版本、治理主体、角色、准入条件、阈值规则、策略引用、信任锚、退出及终止程序。重大变更由治理提案驱动：提案哈希绑定 Space ID、治理版本、有效期和操作内容；各方签名或模拟签收；服务执行前验证门槛与前序版本，写入不可任意改写的审计事件。签名不能自动解决分布式一致性，仍需单一序列或冲突协调机制。

实验室的设备操作权限必须由实验室安全责任人决定；客户的配方授权必须由客户控制者决定；空间治理方可以决定成员准入，却不能自动越过这些控制点。

七、托管服务商：治理控制面与运行服务面分离

AWiki 可成为可信数据与可靠协同空间的基础设施托管服务商，但应“托管协同，不强制托管全部数据”。治理控制面负责规则、成员、签名门槛和角色；运行服务面负责消息/事件投递、Board 协同状态、工件索引、授权决策请求、审计、通知和恢复；数据与执行面由客户、材数智元、实验室或第三方自行运行。

建议至少划分四类服务：Space Directory & Governance（目录、准入、治理版本）；Board/Artifact Relay（协同事件、引用、回单）；Policy & Audit（策略决策、执行点集成、审计证据）；Pack Registry（发行、签名、版本、能力声明）。其中策略执行点必须位于真正的数据 API、工件下载、设备适配器等入口；仅在 AWiki 页面上隐藏按钮不是安全控制。

在多方共治中，托管商接收经多方确认的治理事件并执行；在协议自治中，托管商依据已生效的规则验证凭证、能力与条件后执行。托管商应可被替换，空间治理声明、成员状态、工件引用和审计摘要需支持导出、校验与迁移。

服务商失效时，各主体应仍持有自己的身份和私有数据；空间恢复需要验证治理状态、事件顺序、最新授权撤销与未完成任务。跨节点冲突、事件重放、权限缓存过期和部分执行成功等问题，必须在 MVP 之后逐步建立明确恢复语义。

八、Board 与 OA、A2A Artifact 的边界

A2A 已有 Task、Message、Part、Artifact、Agent Card 等对象，能够交付结构化数据和任务结果。AWiki 不应把普通 JSON 结果卡包装成新的底层协议。建议保留原生 A2A Artifact，在 AWiki WorkArtifactRecord 中增加业务身份、版本、依赖、授权、验收与长期引用关系；二者通过引用/映射连接。

Board 则是多主体围绕一个工作对象持续维护事实、责任、讨论、版本与证据的协作工件。签收只是其中一个局部动作。若 Board 只有“批准/驳回”，就与 OA 审批没有实质区别；真正差异在于跨主体持续协作、各方独立数据控制、工件互操作与后续复用。

“确认事实”“接受任务责任”“签署法律协议”必须区分。点击 Board 确认或 DID 技术签名，不自动构成具有法律效力的电子签署；需要适用法律、授权代表资格和可靠电子签名体系的额外验证。

Board 默认关联一个空间，但具有稳定 Board ID、控制主体、参与主体和可独立访问的工作页面。Board 在资源中登记；事项群中显示其引用卡和回单；空间专题中可收录其已授权结论；方案包保存 Board 模板与创建规则，而不是某次实际 Board 的副本。

九、Matter、AI 伙伴与人机混合实验

事项是动态创建的人机混合群，而非预先为每个 L 模块建一个聊天室。一个研发项目可因正式委托、方案交接、实验委托、结果回流等工作边界，形成若干事项群。上游交接时只传最小授权快照，不自动继承全部历史聊天、客户私有配方或私人 AI 伙伴备注。

AI 伙伴是人工成员的私人工作面，帮助快速理解当前群任务、执行标准、异常条件和人性化反馈。它不是群成员，不等于 Lab Orchestrator，也不应自动替人签署或启动设备。

L6 的同一 Experiment Task Schema 可以被人工实验员或设备 Adapter 消费。人工路径需要接单、SOP/设备/原料核对和具名回单；自动化路径需要设备权限、可验证状态、安全联锁、停止条件和回单。两条路径共享任务语义但不共享不恰当的安全假设。

十、PET 研发演示：从客户需求到 L7 回流

演示参与主体：客户企业（李工）、材数智元（张研与 L0–L7 Agent）、合作实验室（王工与实验室 Agent）。三方各有独立客户端视角，安装兼容材料科研协同方案包；客户与材数智元按多方共治规则邀请实验室加入 PET 联合研发空间。

客户发起研发委托 Board，明确目标、来源、共享边界和责任。L0 Agent 读取原始需求与 V0.2 建议，自动识别冷热循环口径差异；双方在同一 Board 中讨论并形成版本化结论，而不是为每个异常创建审批表。L1/L2/L3 分别产生筛选、机理、路线建议 Artifact；经交接形成方案事项，L4 规划样品矩阵，L5 生成 TC-01 标准任务卡。

跨机构实验委托必须经空间准入与 Board 授权。实验室安装方案包并加入空间，实验员由私人 AI 伙伴辅助接单；L6 以人工或模拟设备路径生成带来源标记的回单；L7 评价模拟结果和未测项，回流下一轮 L4。最终结果工件登记在资源中，空间专题引用已授权结论，方案可提炼经专家审查的通用任务模板。

重要：源材料建议首轮 8 组聚合样品+3组对照，资源有限时可优先6组主样+3组对照；Demo 聚焦 TC-01 的 PETE-A1/A2/A3，PTMG 10–12/15–18/20–22 wt%。所有模拟数值均非实测。

十一、数据结构与协议映射建议

Pack Manifest 声明业务协议、Schema、角色、能力与兼容版本；Space Governance Manifest 声明空间治理和策略；Board Record 声明共同事实、控制主体、参与者、版本及事件；WorkArtifactRecord 为 A2A/文件/数据集增加长期引用、依赖和验收元数据；Matter Handoff 定义最小共享快照、责任和回单契约。

所有 JSON 只是设计样例，非已发布的 AWiki 标准。A2A Artifact 的真实字段及语义应按对应协议版本实现，不能把 AWiki 扩展字段当作 A2A 核心规范字段。ANP/OVAIM 在这里是待接入的身份与授权机制，不代表已完成真实互操作。

建议策略判断输入包含主体身份、Agent 代理关系、Pack 兼容版本、Space 角色、Board 控制策略、工件数据分类、用途、有效期和风险等级。PDP 返回决定，PEP 在实际数据/设备接口强制执行，并写入审计。

十二、V5 Demo 与说明书的对应操作脚本

打开 V5 HTML 后，默认进入“工作→空间→空间概览”，可见 PET 联合研发空间及第二个独立演示空间。顶部“当前客户端”可切换客户、材数智元、实验室视角；这是用于讲解的模拟身份切换，不是实际登录或权限认证。

第一幕（2分钟）：打开“工作→方案”，观察三个客户端的安装状态，说明安装兼容 Pack 是加入空间的能力前提，但不等于自动入会。返回“空间→成员与治理”，观察客户与材数智元是联合治理方，实验室尚未加入。

第二幕（3分钟）：切回材数智元，进入“工作→事项”，按 N 逐条推进。L0 Agent 自动发现需求表与 V0.2 的温度口径差异；点击研发委托 Board，查看共同事实、协作记录、版本、主体与权限。切换客户/材数智元两个模拟客户端分别签收，才能冻结 Board 版本。按 N 继续至 L3 的方案交接。

第三幕（3分钟）：在 L4/L5 消息中点击输入和输出工件卡；进入“工作→资源”，查看 A2A 风格 JSON、AWiki WorkArtifactRecord、上游依赖与下游接收者。强调“消息说做了什么，Artifact 证明交付了什么，Board 说明谁共同确认”。

第四幕（3分钟）：推进至实验委托关口，系统会阻止未加入实验室的执行。转到“空间→成员与治理”，客户与材数智元分别确认治理提案 G-017；切换实验室客户端安装 Pack、接受加入邀请。回到事项中的实验委托 Board，由研发方和实验室分别模拟签收。实验员再由自己的 AI 伙伴辅助接单，选择人工或模拟设备执行并生成 L6 回单。

第五幕（2分钟）：L7 生成评价工件并形成下一轮交接；空间专题可引用长期知识，方案保留可复用模板。进入“空间→演示管理”，导出、只读回放、复制演示空间、恢复当前空间初始快照。复制后重置新空间，切回原空间确认其进度与 Board 未受影响。

十三、空间级演示重置、回放与复制

演示状态应绑定 Space ID，而不是全局浏览器或整个方案包。推荐三种不同动作：只读回放（只改变观看进度，不更改业务记录）；恢复初始快照（清除本空间的模拟运行事件、Board 签收、Artifact 登记、备注与回单）；复制演示空间（生成新 Space ID 与独立运行状态）。

演示空间可以配置演示主持人操作重置，但这不是空间管理员自动拥有的真实数据删除权。真实空间应采用归档、撤销、保留策略与依法处理，而不是任意擦除审计记录。即使在模拟中，重置前也应支持导出、二次确认并明确影响范围。

V5 HTML 实际采用独立本地存储命名空间，空间状态分别保存；Pack 安装状态为独立客户端级配置。重置某空间不卸载 Pack、不修改其他空间。只读回放不会重写确认记录。由于该 Demo 为纯前端，浏览器身份切换和存储隔离不能被视为真实多租户安全隔离。

操作是否修改运行状态是否影响其他空间生产系统对应操作

十四、MVP 路线：先托管协同，再验证联邦互操作

阶段一（可演示的产品闭环）：完成 Pack 安装与兼容检查、空间创建与邀请、治理声明、单方/双方确认、事项群、Board 共同事实与回单、Artifact 输入输出链、资源索引、空间级重置。采用单一协调服务托管，但数据控制和签收语义明确分离。验收以真实用户操作、权限阻断和事件回放为准。

阶段二（首个真实跨组织试点）：客户、材数智元、实验室至少各有一个独立身份和服务端点；接入真实 A2A Agent、数据/工件存储 API、OVAIM 授权执行点、审计；至少一条人工实验员真实回单，明确物理实验安全责任。真实材料数据底座接入前需核实可用 API、数据质量与使用约束。

阶段三（多服务商与联邦）：跨服务商 Board 引用、签名治理事件同步、空间迁移、故障恢复、版本协商和多节点冲突处理。需要独立安全审计、隐私影响评估和专业领域合规评估后才可推广。

商业化可将基础协调服务按空间/成员/事件量计费，专业 Agent/Skill 和行业 Pack 按能力付费，数据提供方继续按自身许可收费；不应通过默认集中托管客户原始数据获取平台锁定优势。

阶段可验证交付关键验收
MVP-1三方客户端演示、Pack/Space、Board/Artifact、重置权限门槛不被 N 跳过，跨空间状态隔离
MVP-2真实身份/授权、跨机构任务、人工回单独立主体端到端任务可追溯
MVP-3多节点互操作与迁移故障恢复、撤销一致性与兼容测试

十五、关键风险、边界和治理问题

“可信数据空间”不是安装 Pack 就天然成立。真实可信需要可验证主体身份、具体目的与时效的信任评估、数据使用协议、强制策略执行、审计与异常恢复。信任不应自动跨主体、跨空间或跨合同传递。

跨空间 Board 引用有上游授权约束、缓存版本、撤销后已有副本、知识泄露与责任分配风险。建议默认不共享，显式授权、限定字段、冻结版本或派生新 Board，并保存来源与撤销事件。数据使用控制不能保证接收方已经获得的明文副本被技术上完全收回。

多方签名保证授权事件可验证，不自动保证事件顺序、可用性或法律效力。空间托管商被攻破、参与方私钥泄露、Agent 越权、模型幻觉、实验设备危险操作、材料知识产权归属和跨境数据处理，都需要单独威胁建模与合规设计。

科研数据的证据等级必须明确：原始实测、经复核实测、仿真、模型预测、文献引用、研究假设、纯演示。任何模拟值不得混入真实验收报告。用户看到的“已确认”仅指演示角色点击，不代表真实数字签名或客户授权。

十六、对外定位与可复用表述

产品定位：AWiki 是以方案包组织协同能力、以可信空间建立协同边界、以共同工件连接独立主体的开放式可信工作网络。

方案包：安装在不同用户、组织及其 Agent 客户端中的可复用协同协议与能力包，使各方能够理解并处理兼容的 Board、Artifact 与 Resource。

空间：由安装兼容方案包并建立授权关系的主体组成的可信数据与可靠协同边界，具有独立治理规则、成员、授权和工作状态；同一方案包可以支持多个空间。

事项：按具体工作动态形成的人机混合群；Board 是需要共同维护事实、承诺与验收时建立的持续工件；Artifact 是任务产生的结果；资源统一登记可用工件；专题在空间内部组织长期知识。

服务商定位：AWiki 可托管空间协调、工件协作、策略与审计基础设施，但不因此拥有空间治理权、成员私人数据或设备操作权。
